# Persistence and Local Data

## Default rule

AI Booster Kit does not have one hidden global state store. Each subsystem owns
its data explicitly. Read-only and pure commands must not create persistence;
commands whose purpose is to save state name the target or application-data
root in their interface.

## Storage map

| Surface | Persistence behavior |
| --- | --- |
| `booster` / `projectDeliveryCompass` | None. Reads one request and canonical Registry; writes JSON only to stdout/return value. Artifact references remain caller-owned. |
| Plugin `scripts/booster.mjs` | None. Reads a file or stdin plus its packaged Registry; writes JSON to stdout. It resolves no global session store. |
| `compose-flow` | None. Reads one request and canonical repository contracts; writes JSON only to stdout. |
| `assess-flow` | None. Reads one assessment and canonical repository contracts; writes default JSON or explicit Markdown only to stdout. Receipts remain caller-owned. |
| Flow examples | Repository fixtures under `examples/`; they are not live run state. |
| Owner identity | On supported Windows hosts: `%LOCALAPPDATA%\AI Booster Kit\owner-identity.json`. Written only by explicit setup/reconfigure. |
| Activation packages | `save-activation --input ... --target ...` writes the explicit target; Team retention also requires `--repository-root`. |
| Work context/session | `save-context` and `save-session` write an explicit `--target`; Team retention is repository-relative and requires `--repository-root`. |
| Execution subsystem | `prepare-execution` derives a workspace-specific database from explicit `--workspace` and `--app-data-root`: `<app-data-root>/AI Booster Kit/execution-workspaces/<workspace-id>/execution.sqlite` on Windows (`ai-booster-kit` on Linux/macOS). |
| Build output | `dist/` is compiler output and is regenerated by `npm run build`. |
| Generated plugin files | `plugins/ai-booster-kit/scripts/booster-compass.mjs`, packaged Registry/Planning-Show, and `claude-skills/` are tracked distribution artifacts regenerated by `npm run package:booster`. They are not live session state. |

## Booster artifact ownership

A Compass request is a caller-owned snapshot. `artifact.reference` points to
workspace or host evidence and `artifact.state` is the caller's declaration.
The Compass validates structure, exact plan binding, and gate state, but does
not read, authenticate, or persist the referenced bytes. A Stage Skill must
reopen material artifacts before acting.

`compassId` is reproducible from the complete normalized request and Registry.
It detects changed input; it is not a signature, user identity, receipt store,
or approval token.

## Flow receipt ownership

Flow Assurance is intentionally stateless. The caller decides where receipts
live and supplies the complete current set on every assessment. This makes the
same input reproducible across a CLI, test, CI Adapter, or future UI without
making a host database canonical.

Recommended receipt-storage properties:

- append rather than overwrite prior accepted facts;
- retain the complete request and returned `packageId`;
- retain artifact/evidence references and content digests;
- store human decisions separately with access control, then reference them;
- avoid raw prompts, reasoning, credentials, tokens, cookies, or personal
  absolute paths;
- protect the store according to the sensitivity of referenced work;
- never reuse receipts after the request/package identity changes.

These are operator/storage requirements. The pure assessor validates the
receipt contract but does not claim that a caller's storage is durable or
tamper-proof.

## Explicit save safety

Context, session, and activation storage validates retention and target
boundaries. Team targets must be repository-relative and remain within the
resolved repository root. Personal targets are explicit paths. Ephemeral
artifacts cannot be persisted through the save interfaces. Existing different
content produces a conflict rather than silent overwrite.

Execution storage is separate. Its workspace and application-data roots must
be absolute, regular directories and must not overlap; workspace IDs derive
from normalized workspace identity. Flow commands neither create nor open the
execution database.

## Generated and historical material

Historical and optional surfaces are classified in the
[separation inventory](../project/separation-inventory.md). Moving or deleting
them requires a separate migration with citation updates and verification.

## Backup and deletion boundary

This handbook documents locations; it does not authorize backup, movement, or
deletion. Before any destructive action, resolve the exact target, verify that
it belongs to the intended subsystem/workspace, and obtain the authority
required by the repository contract. Git publication and external backup are
also separate decisions.
